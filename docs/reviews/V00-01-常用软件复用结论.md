## 结论先行

1. **收报最小接入候选是 fldigi：作为独立进程、只收不发、经本机 XML-RPC 读取解码文本。** fldigi 4.2.13 内置 XML-RPC 服务（`--xmlrpc-server-address/port`），`rx.get_data` 的文档语义就是“返回自上次查询以来收到的全部 RX 数据”，`text.get_rx(_length)`/`text.clear_rx` 提供文本窗读取与清空。它可跨 Windows/Linux/macOS，源码为 GPLv3。代价是 GPL 分发边界、GUI 进程依赖，以及同一个 XML-RPC 面里同时存在发报/改频方法，必须收窄。
2. **本轮将N1MM+用作流程参考，不作为0.0运行组件。** 它的 CW Reader 是“只收”窗口，由 fldigi/CwGet/外接 TNC 作引擎，且要求 fldigi 关闭 rig control 与 PTT；发报另走其他键控路径，文档提供Esc停止操作。日志/分数/状态广播不能当作完整收发API；官方另列外部设置频率等入站消息，不应概括为所有UDP都是单向。`IsTransmitting` 不覆盖外部PTT/手键，不能当发射证明。
3. **DXLog 提供发送语义，但不复制代码或反射框架。** 静态证据显示 `CWKeyer.CWKey` 把“入队/发送/停止/等待停止/事件”分开：`AddToQueue`、`SendCWText`、`Stop`、`StopWithCR():bool`、`WaitForStop`，并有 `MessageStarting/Stopped/Finished/CharSent` 事件；`DXLog.net.Radio` 是名字反射桥（频率/带宽/发射焦点/报文完成）。这些是“事件不是返回值”的现成范例，但事件存在不等于真实键控完成或物理停发。
4. **不要为 0.0 新建解码器、Fake 核心或第二套设备会话。** 本轮证据支持采用解码与键控分工、区分状态广播与命令、收窄调用能力；这属于对本项目的设计判断，不能概括为三款软件全部采用同一架构。

## 可直接采用的经验

1. **解码器只收，发报另路。** 采用 N1MM CW Reader 的分工：fldigi 只负责声卡→文本，关闭其 rig control/PTT；我方 `CwTrialSession` 仍是唯一发报路径。禁止把 fldigi 的 `main.tx`/`text.add_tx*` 接入，避免两条键控路径。
2. **排空式文本接口只能有一个消费者。** `rx.get_data` 每次取走“上次以来的数据”；GUI 与 CLI 不能各自轮询。共同核心做唯一 poller，把带序号/时间的文本块扇出给两个界面。这是 ADR-021“共享同一控制核心”的具体落点。
3. **发送语义用“入队 + 显式停止 + 等待停止 + 事件”，不要用单个阻塞返回值。** 借鉴 DXLog 的 `AddToQueue/WaitForStop/Stop/StopWithCR` 分层；但只作为 `CwTrialSession` 后续演进参照，不新增 keyer 平台。事件仍须区分“已排入/已发出字符/键控器报告停止”，不得等同射频完成。
4. **边界用能力白名单，不用“默认全开”。** fldigi 有 `--xmlrpc-allow/deny`（按方法名正则），DXLog 的反射面本质也是一张动词表。0.0 的 AI/UI 只应看到“读文本、取状态、提案、请求停止”等命名动作；物理层留在宿主。
5. **报文模板是数据，不是代码。** DXLog 的 `CFGDataCWMessage` 只是 `CWMessage1..7/INS/PLUS` 等字符串字段；这支持把常用报文/宏放配置并做版本校验，而不是编译进流程。

## 优先接入候选与下一交付

**候选：V00-02 的“fldigi 收报薄适配 + 单一文本流”**，不选 N1MM/DXLog 作运行时组件。

- 输入：已有或后续明确安装的fldigi（本次核对源码4.2.13，实际使用版本需记录）；本机回环端口，优先P0-004既有WAV，不以接电台作为离线准备前提。是否由用户自装或以后随包交付未定，本轮不替用户确定分发方案。
- 输出：共同核心的 `RxChunk{seq, text, receivedAt}` 事件流；CLI 先显示文本；GUI 后续复用同一流。不改 `CwTrialSession`、不新增串口会话、不新增持久化格式。
- 启动参数（写入适配器配置，不写死）：`--xmlrpc-server-address 127.0.0.1`、显式端口、`--xmlrpc-allow` 仅放行读取类方法（`rx.get_data`、`text.get_rx`、`text.get_rx_length`、`fldigi.name/version/list`），并在 fldigi 侧关闭 rig control 与 PTT。
- 验收：受影响接口用最少用例覆盖文本顺序、断连显式报告、只读调用；再以一个既有WAV确认实际解码文本能进入CLI。WAV按实际内容判定，不预设每个样本均含呼号。不打开串口、不开TX/改频能力；未修改设备代码/接口则沿用其已有证据，不重跑CwTrialSession。首切片不做完整性能矩阵，仍记录一次样本的实际输出与可见延迟限制。
- 不做：不打包/静默安装fldigi、不造解码器、不接N1MM/DXLog运行组件、不启动自动发射；不建新设备会话或持久化格式。承认引入一个既有外部解码进程和XML-RPC依赖，不能写成零进程/协议增量；不另建自定义服务或通用RPC平台。
- 待核实（写入任务而非预先假设）：WAV 如何送入 fldigi（声卡回放/虚拟声卡/自带文件播放）；fldigi 默认 bind 地址；`--xmlrpc-allow` 在 Windows 版的实际行为；GPL 分发边界（0.0 仅要求用户自装，不捆绑）。

## 后台组件边界复核（2026-10-20，用户纠正后）

用户要求：解码器在后台、本项目GUI/CLI负责全部操作；不能只用解码组件就另寻方案。此前Codex先验证XML-RPC、后检查GUI部署边界，遗漏了产品集成条件，接口通过不等于组件可用。

fldigi实际4.2.10 `--help`只有`-iconic`（最小化）和`--wfall-only`（保留瀑布界面），没有声明headless解码模式。既有4.2.13 `fldigi-main.cxx:1136`附近启动FLTK，1159创建主窗，1272起显示主窗。现有XML-RPC依赖完整应用；本次未发现官方可直接使用的独立CW解码库，不能断言源码绝对不可拆，但本项目不为此拆改整套fldigi、引入虚拟显示或长期隐藏窗口。原适配冻结为实验，不继续WAV GUI调试。

最小候选为[multimon-ng](https://github.com/EliasOenal/multimon-ng)：本轮读取官方README、`demod_morse.c`与COPYING。README明确列出MORSE_CW、文件/stdin输入、无音频库时DUMMY_AUDIO构建和Windows MinGW/MSVC支持；`demod_morse.c`提供22050Hz Morse解码实现。它是无GUI命令行引擎候选，不是已确认的可嵌入库；后台子进程形态符合组件方向，是否采用仍需样本与部署边界证据。整体COPYING为GPLv2文本，单文件public-domain声明不能外推整个程序许可。

仅做本候选必要核实：用已有CQ TEST WAV检验输出内容、实时管道刷新/退出和最小Windows发布依赖。尚未安装、构建、运行、测准确率或修改产品接口；未认定其性能优于fldigi，不展开第二轮软件普查。样本可用后才提交最小替换安排，沿现有cwrig/共同核心，明确旧fldigi适配冻结与回退，不双线扩建。
