### F1（S2）P2-001 接受的 ASCII 字符集宽于 IC-7300 手册的 CW 报文字符表

- 要求来源：任务 `REV-001-P2交叉审议.md:13` 明确要求核对"P2-001 ASCII 字符集是否确实符合 IC-7300 手册而非假定全部可打印 ASCII"；`IC-7300-connection-notes.md:35` 只说"内容为手册所列 ASCII 字符"，从未枚举。
- 期望行为：只接受手册 CW 报文（命令 `0x17`）字符表列出的字符。
- 实际行为：`packages/devices/src/civ-tx-plan.ts:106-111` 只判断 `code < 0x20 || code > 0x7e`，即接受**全部可打印单字节 ASCII**；代码注释 `civ-tx-plan.ts:90-96` 明确写的是 "printable single-byte ASCII"。
- 手册实际字符表（官方 IC-7300 操作手册印刷页 19-11，命令 `0x17`，"Up to 30 characters"）：
  - `Space` `0x20`，`"` `0x22`，`'` `0x27`，`(` `0x28`，`)` `0x29`，`+` `0x2B`，`,` `0x2C`，`-` `0x2D`，`.` `0x2E`，`/` `0x2F`，`0-9` `0x30–0x39`，`:` `0x3A`，`=` `0x3D`，`?` `0x3F`，`@` `0x40`，`A-Z` `0x41–0x5A`，`a-z` `0x61–0x7A`。
  - 同页注明 `0xFF` 停止发码、`^` 表示无字符间隔的连续发码（`^` 未列入上表，但被手册作为功能字符说明；P2-001 接受 `0x5E`）。
  - 上表**未包含**但 `civ-tx-plan.ts` 会接受的字节包括：`!` `0x21`、`#` `0x23`、`$` `0x24`、`%` `0x25`、`&` `0x26`、`*` `0x2A`、`;` `0x3B`、`<` `0x3C`、`>` `0x3E`、`[` `0x5B`、`\` `0x5C`、`]` `0x5D`、`_` `0x5F`、`` ` `` `0x60`、`{` `0x7B`、`|` `0x7C`、`}` `0x7D`、`~` `0x7E`。
- 触发场景：
  - `node --import tsx apps/cwrig.ts tx --dry-run --text "CQ TEST!"` → 当前会成功并输出含 `21` 的帧，而 `!` 不在手册 CW 字符表内。
  - `cwrig tx --dry-run --text "A#B"`、`"DE [CALL]"`、`"OK~"` 同理。
- 影响：当前仅离线规划，`executable:false`，不会发射，故不构成 S0/S1。但该 plan 会被未来的 P2-003 真实适配器当作"已校验文本"直接使用；对手册未定义的字节，电台行为（忽略、替换、异常发码或拒绝）未知，且可能破坏已批准内容与实发内容的一致性。测试 `tests/civ-tx-plan.test.ts:39-45` 只覆盖空串、中文、换行、超长和 `^`，**没有任何逐字符或反例边界**，无法暴露该偏差。
- 修正建议：
  1. 用**手册字符表白名单**替换 `0x20..0x7e` 谓词；`^` 按手册"连续发码"语义单独处理并注明。
  2. 为手册列出的每个字符加正向用例，为未列出的至少 `! # ; [ ] ~` 加反向用例。
  3. 在模块注释与证据中记录手册页码/表来源，并在仓库内转录该表（见 F9）。
- 未验证范围：手册未定义字节能被固件如何解释，本审议无法验证；不得假定"发得出去就等于电台接受"。

### F2（S1，设计草案）`cw.send` 操作 ID 由服务端生成，缺少客户端稳定幂等键，响应丢失后可能重发

- 要求来源：`REV-001-P2交叉审议.md:13`（"操作 ID 和响应丢失后的防重发"）；`任务自查与审议规范` R06/R07。
- 期望行为：每个受控写入有稳定、可复现的操作 ID；响应丢失、连接断开或服务重启时，重复请求必须被识别并返回既有结果，绝不二次键控。
- 实际行为（草案）：`docs/design/P2-002-设备持有者与受控写入.md:32` 写"`cw.send`：**服务端生成 request id**，参数为已校验文本、上下文代次和一次性操作 token"；`cw.stop`（`:33`）没有 ID；全文没有"不自动重发"的约束，也没有幂等表/去重规则。"一次性操作 token"若每次重试重新生成，则不能充当幂等键。
- 触发场景：daemon 通过 `RemoteKeyer` 发出 `cw.send`，设备服务已键控电台，但在写回结果前 IPC 断开/超时；`TxController` 如实判 `unknown`。此后若客户端重试、或服务在重连后重放、或操作 token 被重新铸造，服务端会生成**新的 request id** 并再次发码 → 空中重复发射，且无法证明停止。
- 与现有实现的关系：daemon 侧已按提案 ID 幂等，不重发（`tx-controller.ts:511-519`）；CI-V 本身无事务 ID，无法靠协议区分归属（`civ.ts:10-11`、`serial.ts:20-22`）。因此**幂等责任必须由设备 IPC 契约补上**。
- 影响：违反"不自动重发、不把未知当完成"的核心安全契约；真实写入后可能导致未授权重复发射。设计未实现，故当前不构成现实 S0，但阻止 P2-002 作为实现基线。
- 修正建议：
  1. 由**调用方**（`TxController`/`RemoteKeyer`）生成稳定 `operationId`（例如 `proposalId + attempt`）并随 `cw.send` 传入；设备服务必须持久化/记录已处理 ID 与结果，重复 ID 返回原结果、不重复键控。
  2. 明确"同一 ID 携带不同文本/上下文"必须拒绝，不得静默覆盖。
  3. `cw.stop` 也必须有独立 ID 与目标 `operationId`，并定义重复停止的幂等语义。
  4. 契约中显式写入：设备服务与客户端均**不得**在超时/断线后自动重发或自动重连重放。

### F3（S1，设计草案）唯一设备持有者的迁移/切换未定义，存在第二个 COM17 持有者的风险

- 要求来源：ADR0008:8-13（"不增加第二个串口持有进程"、"真实后端必须先解决唯一设备持有者"）；ADR0007:12-15；R05/R08。
- 期望行为：任一时刻只有一个进程持有 COM17；切换有明确顺序、独占证明与回退路径。
- 实际行为（草案）：P2-002 `:11-16` 列候选 A/B/C，`:17-26` 推荐"B 的逻辑边界，分阶段实现"，但**没有决定第一阶段由谁持有端口**；`:19` 同时说"设备服务是 COM17 的唯一持有者"，`:23` 又说"只读 status/watch/reconnect 保持现有语义和客户端兼容"。现有已真机验收的持有者是 `rig-statusd`（MEMORY P1-007）；设计没有给出 `rig-statusd` → `rig-controld` 的停机、交接、回退步骤。
- 触发场景：迁移期 `rig-controld` 启动并打开 COM17，而 `rig-statusd` 仍在轮询；或把受控写入直接加到只读服务而两个客户端分别触发 reconnect/写入。串口层的同进程登记只防同进程重复（`serial.ts:309-320`、`:785-792`），跨进程独占仅靠 OS `lock:true`（`serial.ts:8`），本审议未验证其可靠性。
- 影响：两个进程在同一 CI-V 总线上交错字节；由于 CI-V 无事务 ID，字节归属不可判定，既可能误读状态，也可能在非预期时刻写入。违反唯一持有与 R08。
- 修正建议：
  1. 明确第一阶段单一持有者：要么在 `rig-statusd` 内增加**独立、受 ACL 保护**的控制端点（候选 A，但须做只读/读写能力隔离），要么先停 `rig-statusd` 再起 `rig-controld`（候选 B），并写清停机顺序、端口释放确认与回退。
  2. 增加启动时的独占证明：若另一持有者存在则拒绝启动；把"当前持有者"写入 `doctor`/状态输出。
  3. 受控写入使用**独立的结构化写入 transport 模块**，不修改 `serial.ts` 的只读白名单（`serial.ts:83-88`、`:481-496`）。

### F4（S1，设计草案）控制通道权限模型未定义，只读客户端可能触达 `cw.send`

- 要求来源：`任务自查与审议规范` R08；MEMORY"AI 只提案或建议"、"CLI 批准不能证明真实人类参与"；`REV-001-P2交叉审议.md:13`（"控制通道权限"）。
- 期望行为：只有 daemon 能调用结构化写入；CLI/界面/AI 只能走 daemon 的提案/批准接口；控制端点在创建时即具备与只读端点同等或更强的隔离。
- 实际行为（草案）：P2-002 `:26` 只写"CLI、界面和 AI 只能访问 daemon 的提案/批准接口"，但没有定义控制 IPC 的端点类型、文件模式/ACL、能力令牌或调用方身份校验；`:30-36` 的 `cw.send` 对任何能连到该端点的进程都是可调用的。
- 触发场景：
  - 若控制方法与 `status/watch` 共用同一 Unix socket（0600）或命名管道，则任何同 OS 用户进程（包括被授予 shell 的 AI 进程）都能调用 `cw.send`，绕过 daemon 的一次性批准与审计。
  - 若 Windows 命名管道未采用创建时受保护 ACL，则权限边界退化；现有 `bridge.ts:139-151` 已实现创建时 ACL 读回校验，设计未说明复用。
- 影响：违反"AI 只提案"、"批准绑定具体内容"的边界；实现后可能是 S1。
- 修正建议：控制端点与只读端点分离；Unix 0600/父目录 0700、Windows 创建时受保护 ACL（复用 `WindowsBridge` 的校验）；增加由 daemon 铸造的**单次操作 token**（绑定内容 hash、频率/模式、连接代次、有效期）；只读客户端不得列出/调用控制方法；文档明确同用户仍是信任边界，不证明人类批准。

### F5（S2，设计草案）`cw.stop`/`device.close` 与在途 `cw.send`、reconnect 的协调未定义

- 要求来源：R06/R07；`REV-001-P2交叉审议.md:13`（"重连/关闭协调"）。
- 期望行为：停止请求抢占普通写入；在途写入在停止/关闭/重连胜出时归为 `unknown`（不得报完成）；关闭后有界释放并如实报告哪些操作未决。
- 实际行为（草案）：P2-002 `:33` 只写 `cw.stop`"抢占普通控制请求，返回'已发送停止请求'或'无法确认'"；`:34` `device.close`"撤销在途许可并有界关闭串口"；`:25` 提到连接代次，但没有定义：抢占的判定点、写入队列的串行化、状态改变/重连时在途 `cw.send` 的结果映射、以及通知 daemon 的机制。
- 触发场景：
  - `cw.stop` 在 `cw.send` 写入过程中到达，二者竞态；停止可能被普通请求排队在后而延迟。
  - 显式 `reconnect` 在 `cw.send` 在途时发生；旧连接上"已写出"的字节与新连接的状态无法区分。
  - `device.close` 超时后只返回"无法确认"，但未定义在途 send 的结果，daemon 可能沿用旧状态。
- 影响：无法区分"已请求停止"与"已确认停止"，可能把未证实的停止写成完成；违反 R06。
- 修正建议：设备服务内单一串行命令队列 + 连接代次；`cw.stop` 立即抢占队列并使当前代次失效；被抢占/被关闭的在途 `cw.send` 一律解析为 `unknown`，不得为 `completed`；`device.close` 有界返回并列出转为 `unknown` 的操作；`reconnect` 递增代次并使旧代次所有在途结果失效。可参考只读服务已有的代次与释放顺序（`service.ts:384-406`、`:537-559`、`apps/rig-statusd.ts:157-173`）。

### F6（S2，设计草案）Fake IPC 故障矩阵只有一句前置条件，未列出用例

- 要求来源：`REV-001-P2交叉审议.md:13`（"Fake IPC 矩阵"）；R07。
- 实际行为（草案）：P2-002 `:40` 仅写"先为 `RemoteKeyer` 建立 Fake IPC 和断线/迟到回执测试"，没有矩阵。
- 影响：无法验证 F2/F5 的契约；P2-003 之前缺少回归基线。现有只读测试（`service.test.ts:129-211`）只覆盖读会话的 fault/reconnect，不覆盖结构化写入。
- 修正建议：至少覆盖——
  1. send 成功且 ack 正常；
  2. send 已键控但 ack/回执丢失；
  3. 同一 `operationId` 重复 send（同文本/不同文本）；
  4. stop 在 send 前/写入中/写入后到达；
  5. reconnect 在 send 在途时发生；
  6. 服务重启时存在在途操作（启动后应为 unknown，禁止自动重发）；
  7. 超时后迟到的 ack/完成；
  8. 写入期间设备断连；
  9. IPC 连接在键控后断开；
  10. stop 无法确认；
  11. close 与 send 竞态；
  12. 帧超限、非法方法、控制字段注入。
  每项都要断言"没有第二次键控"和"结果非 completed 的路径为 unknown"。

### F7（S2，设计草案）跨边界消息长度契约不一致：daemon 允许 400 字符，IC-7300 上限 30 字节

- 依据：`tx-controller.ts:84` `DEFAULT_MAX_TEXT_LENGTH = 400`、`:405-407` 只按 400 校验；ADR0008:18、`civ-tx-plan.ts:15`,`:101-103` 规定 30 字节上限。
- 触发场景：一条 60 字符提案可通过 `propose`/`approve`（内容 hash 绑定 60 字符）；未来 `RemoteKeyer` 转发给设备服务时，若服务拒绝 → 批准已被消费却无法执行（unknown）；若服务截断 → 实发内容与批准 hash 不一致。
- 影响：授权内容与实发内容不一致、unknown 语义混乱。R04/R05。
- 修正建议：在 `RemoteKeyer`/设备边界强制执行 30 字节并**复验内容 hash**；在设备能力声明中体现长度上限；daemon 的提案上限宜由设备能力推导或在批准前按目标设备校验；**禁止在批准后截断**。当前无 `RemoteKeyer` 实现，故不是现存缺陷，但必须在 P2-002 契约中先定。

### F8（S3，设计草案）控制 IPC 缺少协议版本与审计元数据

- 依据：P2-002 `:28-36` 未出现协议/契约版本字段；对照 `server.ts:279-297` 强制 `protocolVersion`，`RigStatusIpcServer` 只接受 `id/method/params`（`service.ts:586-611`）。
