# CW 台站方案审阅意见

审阅日期：2026-10-05。对象：`CW台站方案_审阅包_20261005.zip`。

结论：**认可方向，建议修订后开展范围受控的 Phase 0；当前文档不足以作为接真机发射的实施基线。** 保留 Python、CLI、开源组件复用、不 fork 应用及独立前端方向。需要重写授权与故障恢复契约，明确日志真源，收缩第一阶段范围。无需重搭平台。

本次通读主方案，交叉审阅架构、兼容性附录及相关原始材料，并通过上游源码/文档核对关键接口。没有安装运行台站组件，没有连接电台，没有做射频、时序或硬件验证。下文区分文档错误、上游已核实事实、设计缺口及待测假设。审阅包原文保持原样。

## 一、按严重程度排序的发现

### P0-1：方案宣称的人控授权，在现有契约中没有成立

位置：主方案第 201、221–238 行；第 91 行附近“把规则仲裁器换成模型仲裁器”。

L2/L3 表格要求每条发射由人触发或确认，但实现说明却采用“提案自带 `min_auth_level` 与当前档位比较”；裁决示例是 `approved ... by: policy:L2`。档位比较不能证明人批准了这条消息。由智能体自己申报所需权限也不是可信授权依据。

提案还没有绑定电台实例、实际 TX 频率/VFO、模式、发射内容摘要、速度、QSO 状态版本和审批身份。人在频率 A 批准后手拧 VFO 到 B，执行器仍可能照发。`expires_ms` 没有服务端创建时刻或截止时刻定义，也没有解决排队、重启或审批耗时。

**建议：**权限由服务端按动作和会话策略计算。人工确认生成一次性批准记录，绑定不可变消息摘要与操作上下文；执行前再次校验真实电台状态、审批有效期、TX 互斥及后端能力。上下文改变就作废。确定性的许可检查、互锁、急停和超时不能被模型仲裁器替换；模型可提建议或排序候选。

### P0-2：`T 0` 不是所有 CW 后端的可靠停发动作，看门狗也安排得太晚

位置：主方案第 1.1、9.1、11 章；兼容性附录 B2。

CW 的 KEY、PTT、CAT 发码队列并非同一种状态。采用 break-in/QSK 时，KEY 仍可能触发发射；CAT 下 PTT 不能据此证明 KEY 已释放或队列已清空。同一个失效的 CAT 连接也不能可靠执行兜底命令。父进程或同一事件循环里的看门狗无法覆盖它自身挂死。

此外，Phase 1 已接真后端，而看门狗、重连等被放到 Phase 3。这与方案“发射看门狗是硬要求”冲突。

**建议：**首次接真机前完成分后端的 `abort/clear_queue/release_key/release_ptt` 契约，明确哪些可观测、哪些只是尽力执行。急停应抢占普通命令队列；暂停/恢复、USB 拔插、CAT 失联、执行器退出均默认撤销发射许可。需要抵御整个主机失效时，依赖电台/键控器的独立超时或硬件互锁，并实测其覆盖范围。30 秒应是结合设备、功率和工作周期确认的配置，不是通用安全保证；也不能断言超时必然烧功放。

### P0-3：对不确定的 UDP 发射结果，缺少恢复规则

位置：主方案第 9.1、7.1 章；兼容性附录 B2。

`^` 是后端完成回执，不是带请求 ID 的可靠事务协议，更不代表对方收到。回执丢失时，消息可能已发完；超时重发则会再次发射。旧回执还可能被误当作新请求的完成消息。CLI 层写“幂等”无法自动消除电台这一外部副作用。

**建议：**每个键控后端只允许一个在途请求。持久化执行意图、开始、后端完成和结果未知等状态；按请求 ID 去重。超时、进程重启、取消后的迟到回执均进入明确的恢复流程。无法确定是否已发时，记录 `outcome_unknown`，禁止自动重发或自动记作成功 QSO，待人工处理。清理旧连接/回执并确认后端空闲后再开启新会话。切片和重复发送中止命令只能降低部分风险。

### P1-1：日志真源和 TLF 的角色互相矛盾，WAPC 对账前提未建立

位置：主方案第 4.1、4.3、10 章；架构第 554、565、590、679、689 行；兼容性附录 F。

文档同时主张 TLF 日志唯一真源、自研 SQLite 日志、自研引擎、TLF 仅作校验器、L3 才需要程序写 QSO。实际上 L2 定义已包含“自动记 log”，因此写入问题在 L2 就存在。

上游 TLF 确实有 `-i/--import`，这条没有被推翻。但官方手册明确：导入要依据配置中的规则和 Cabrillo 布局；输入是 `YOURCALL.cbr`，产物是 `IMPORT_contest.log`。它并不意味着默认具备 WAPC 的独立计分能力。本包规则清单没有 WAPC；尚无可复现的 WAPC 配置与对账证据。

**建议：**明确一种模式：自动记录由自有日志存储承载，外部日志器只作导入、导出或可选对账；如果第一阶段坚持 TLF 真源，就限制为人工录入并删除自动记 log 的承诺。TLF 对账列为待验证适配项，不作为当前已成立的验收前提。用年度官方规则、对应 N1MM UDC、人工边界用例建立基准。自研日志与规则执行器是新增实施范围，应明确工作量和交付物。

### P1-2：WAPC 规则包示例连本比赛的完整交换都不能表达

位置：架构第 788–790 行；原始素材 `WAPC_CW_CN.udc`、`WAPC_CW_DX.udc`；背景规则报告第 131–136 行。

`expect: '^(?<rst>...) (?<sect>[A-Z]{2})$'` 只接受省码，而非中国台发送的是 RST + 流水号，例如 `599 001`。直接用于收报会拒绝有效的国外通联。`(?<name>...)` 也不是 Python 标准 `re` 的命名组语法，标准写法为 `(?P<name>...)`。

中国参赛台发送省码，非中国参赛台发送流水号；DX UDC 还有 `PointsMultByCountry`，不能拿 CN 版公式声称覆盖全部参与者。`5NN` 等缩写也需要在严格结构校验前明确归一化策略。

**建议：**明确首版支持“中国参赛台的 WAPC-CW”，但接收必须覆盖中国省码与国外流水号。把交换分支、重复通联键、实体归属、有效时间/波段、计分优先级、导出布局写成有版本的契约。流水号保留原始文本和规范化值。禁止直接 `eval` YAML 中的计分表达式。

### P1-3：Hamlib #1748 被当成当前根因，但它已有修复提交

位置：主方案第 9.1；兼容性附录 B1；审阅指南挑战点 #5。

本次核对：#1748 报告针对 Windows Hamlib 4.6.2 的多客户端响应分隔符混用。维护者指出 `resp_sep` 是全局变量，应改为连接/线程局部变量。提交 `8d0e67f0173d1cd7131c1235997105204cc48dbd` 明确写着 “Fixes issue #1748”，该 issue 在 2025-06-21 关闭。

它证明历史缺陷存在，不能证明目标版本仍有缺陷，也不能扩张为“两个客户端拿到对方答案”。本次读到的 issue 评论没有方案引用的 “Yes, it is broken” 原话。更没有证据证明它解释用户原有 N1MM 掉线；需要先确认原系统是否用了这个组件和版本。

**建议：**记录实际二进制版本并确认包含修复。为权限控制和命令顺序保留单一 CAT 写入者，但不要据此优先开发完整 Hamlib 透明复用代理。首版没有第二个 CAT 客户端时，用串行请求队列即可。故障诊断先采集原系统日志、USB 事件和资源占用。

### P1-4：竞赛合规结论把软件功能、社区习惯和正式规则混在一起

位置：主方案第 6 章；架构第 15.6 节；背景规则报告第 1.5 节。

“FT8 有 Auto Seq，所以 FT8 合规、同样 CW 不合规”推理不成立。软件有功能不能证明具体竞赛或台站许可允许使用。包内背景研究反而写明，没有找到 WAPC 自动化禁止条款；主方案不能把所有 CW 竞赛统一禁 L4 表述成已证实的赛事规则。

这可以是项目主动采取的保守产品策略，但必须与官方禁止分开。每次发射都确认也不自动保证满足所有参赛组别、辅助工具、远程操作或外部数据限制。

WSJT-X 的 Reply 消息等价于双击已解码 CQ/QRZ；一次勾选 Enable Tx 不是逐条审批，也不是不可绕过的安全闸门。模式后端可能自行持续执行后续时隙，必须明确批准的是单条消息还是整通 QSO，以及撤销/截止规则。

**建议：**按赛事年度、组别、模式、所在地与台站许可记录可用能力和规则出处。未知项采用项目定义的保守限制。首版先做确定性的人控策略，不急于实现完整档位矩阵。

### P1-5：进程隔离被宣称为许可证保证，结论过强

位置：主方案铁律 4、第 9.2；兼容性附录第三章。

进程边界是合理工程选择，但是否构成一个结合作品取决于实际组合和通信语义；“不 import”或“TCP 通信”都不是自动免责条件。自己加 Apache-2.0 文件头也不会改变复制代码的许可证。

GPL-2.0-only 与 GPL-2.0-or-later 不能混写。LGPL 更不能简单等同于 GPL/AGPL；它允许在满足条件时与其他许可证代码结合。本包关于 DeepCW 的许可证归属没有固定仓库、提交及模型许可证证据，本次不作已核实结论。

**建议：**把“许可证防火墙”改为“保持组件独立并管理许可证义务”。建立组件/版本/许可证/修改情况/发布方式清单，保留许可声明，履行涉及分发及 AGPL 的适用源码义务。独立通用服务和标准协议有助于支持组件独立性的判断，但不能承诺法律结果。可参考 GNU GPL FAQ 的 mere aggregation/插件边界说明及 AGPL 第 13 条；需要发布组合产品时按实际结构评估。

### P1-6：发射控制部署与仿真入口并未闭环

位置：主方案第 9.4、10 章；兼容性附录 D、L0 命令。

方案只说 Windows 运行 rigctld，没有落实谁在何处持有 CW 键控与音频设备。若 CAT 与 DTR/RTS 在同一串口设备上，两个进程可能无法同时独占打开；若经 usbipd 把设备交给 WSL，Windows 原持有方案又要调整。cwdaemon 的上游验证平台以类 Unix 为主，不能默认 Windows 环节已解决。

`cwdaemon -x n` 只关闭声音，并不自动禁止硬件键控。无硬件仿真应显式使用 `-d null`，并核对所选版本的支持。`rigctld -m 1` 只模拟部分 CAT 行为，不能证明实际 KEY/PTT、射频输出或硬件看门狗有效。

从 `/etc/resolv.conf` 取 Windows 主机地址也不可靠：WSL DNS tunneling 和不同网络模式下该地址可能不是可达宿主地址。

**建议：**先选单一可验证部署路线，画出每个设备和端口的唯一持有进程。宿主地址配置或按网络模式检测。台站后端端口不得直接暴露给有任意 shell 权限的智能体；仅删除 CLI 的 `transmit` 命令不能阻止它直接发送 UDP。若确需防绕过，应用独立账户、设备权限与网络访问限制落实。

## 二、对 12 个挑战点的判定

| # | 判定 | 建议 |
|---|---|---|
| 1 TLF 当引擎/校验器 | 作为可选校验器可探索；当前主日志链路不成立 | 明确自有真源或人工 TLF 真源；验证 WAPC 配置后再声称可对账 |
| 2 加竞赛只加 YAML | 不应作无限制承诺 | 首版只覆盖已定义的规则能力；特殊竞赛允许受控的策略插件。TLF 自带 Python 规则恰好说明纯数据有边界 |
| 3 YAML vs TLF 格式 | YAML 可用；格式不是核心风险 | 关键是语义、schema、版本和测试。无需迁移 45 个竞赛；后续按需求做导入转换 |
| 4 接口即合规墙 | 对正常客户端有效，对任意 shell Agent 不成立 | 明确威胁范围；发射许可与后端访问控制同时落实 |
| 5 三处静默故障 | 历史 bug、协议约束、解码性能是三类问题 | Hamlib 先查修复；cwdaemon 是超限字节被截断，不是必然整包丢弃；解码延迟须固定版本与参数测量 |
| 6 进程边界隔离许可证 | 工程上合理，不能提供法律保证 | 按组件和实际发布方式处理义务 |
| 7 Python 3.13 | 同意用于编排，不需现在引入 Go/Rust | 重模型独立环境；急停不得依赖阻塞 I/O 或模型返回。实时风险主要在调度和接口契约 |
| 8 二维档位表 | 模式/赛事相关方向正确，两个维度仍不够 | 加年度、组别、许可、批准范围；第一版用能力策略即可 |
| 9 计时 vs caret | 两者都用，但承担不同职责 | 时长估算用于进度/期限，后端完成回执用于状态推进；再计设备 RX 恢复延迟。无回执不能当成完成 |
| 10 每驱动 Dummy | 保留可替换接口；不用要求每个类复制一份 | 共用 Fake、协议模拟器和回放即可；必须覆盖断连、超时、重复/迟到回执，不能只有成功路径 |
| 11 cty.dat | 应引入并冻结版本，但不应视为唯一权威 | 保存原文件及 hash，允许赛事实体规则和人工更正；首版 WAPC 洲际分就需要，不能拖到 Phase 4 |
| 12 正式比赛前对拍 | 同意；只比总分仍不充分 | 逐 QSO 比较重复、有效性、实体、分值、系数及导出字段；避免双方共用同一错误规则 |

补充说明：`1200/WPM` 的单位是毫秒/标准点长。总时长需要累加点、划、字符内间隔、字符间隔和词间隔，不能乘普通字符串长度。TLF 调用的是 `cw_message_length`，源码注释也明确称为 estimated；weight、额外间隔、prosign、速度变化、排队及设备时延会改变实际结束时间。

`cty.dat` 是结构化文本，不是二进制。应区分文件数据、解析器和具体赛事的实体定义。有关斜杠后缀、IG9/IH9、TA0/TA1 的断言需要针对固定文件版本与解析器制作边界样例，不能直接归结为文件无法表达。启动时可提示更新，但比赛会话中应冻结规则和实体库，明确批准后才更换。

## 三、已复核事实与仍待验证项

### 已复核

1. Hamlib #1748 有修复提交，issue 已关闭；是否进入用户实际安装二进制仍需核查。
2. WSJT-X 上游 `Configuration.cpp`：`UDPServerPort` 默认 2237；`N1MMServerPort` 默认 2333。两个默认值对应不同用途，端口都应可配置。
3. WSJT-X `NetworkMessage.hpp` 有 Reply、Halt Tx、Free Text、Configure 等报文；Configure 的模式变更在特定条件下可带来频率变化，因此“绝不可能 QSY”也过于绝对。协议没有一个通用的任意拨号频率设置报文。
4. TLF 有 Cabrillo 导入，但依赖规则与格式配置；导入不等于已验证的 WAPC 校验器。
5. cwdaemon 文档写明最多处理单请求 256 字节，超限部分无通知地丢弃，支持 caret request 及 reply escape，回复以 CRLF 结尾。完成回执不等于射频/远端确认。
6. cwdaemon README：默认串口 CW KEY 使用 DTR，PTT 使用 RTS，可交换或禁用 PTT。因此 DTR 是匹配默认驱动的一个配置选择，并非 IC-7300 的唯一可用选择。
7. morseformer 当前 README 声明 Apache-2.0，并给出版本化的准确率/延迟评估；live 源码说明该路径去掉 LM。不能拿未注明版本的“约 4 秒”作为所有深度学习解码器的固定时延或原系统掉线根因。
8. WAPC CN UDC 明确 `CabrilloVersion=3.0`。可作为首版兼容依据；当届官方提交要求还需核对。

### 仍待验证

- IC-7300 正式手册的 USB Keying 菜单、所选适配器输出线、实际驱动和 KEY/PTT 释放行为；本次未取得并核对该机官方手册。不能将 CAT `b` 发码和串口 DTR/RTS 键控混称为同一路径。
- DeepCW 精确仓库、版本、源码及模型许可证；包内证据不足。
- 目标 Hamlib、cwdaemon、TLF 的可安装性及能力，包括 Windows/WSL 组合。
- WAPC 当届完整规则和组别定义；包内所谓“2022 规则说明”主要是规则变更公告，不能代替完整规则。
- 解码器在真实比赛速度、弱信号、多人同频条件下的呼号/交换准确率和响应时间。
- 原 N1MM 故障的实际原因：现有诊断没有复现、版本和日志支持。

这些不阻止纯离线 Phase 0，但其中设备与停发相关项目必须在启用射频前闭环。

## 四、建议的最小实施路线

五层可以作为代码职责分界，不必变成五组服务。第一版保留一个确定性守护进程、CLI 和简单操作界面；重解码器另进程，其他外部组件按需独立运行。七八个业务“智能体”先实现为普通模块/状态机，LLM 可在后续提供建议。

1. **Phase 0：离线协议与故障闭环。** 定义权限、一次性审批、操作上下文、单在途发射、急停、结果未知及重启恢复。一个 FakeRig + 一个 FakeKeyer；人工录入 QSO；先支持 general 与 WAPC-CW 中国参赛台。用合成音频起步，真实录音单列数据来源。
2. **Phase 1：一台电台、一条键控路线。** 明确 CAT、KEY/PTT、音频唯一持有者；先假负载，再有人在场的日常通联。验证取消、断连、拔插、休眠、进程退出与射频停发。未通过就不开放自动呼叫循环。
3. **Phase 2：日志及有限辅助。** 历史日志与边界样例逐项对账，确认导出可接受；一个解码器只提供抄收建议，人工确认呼号和交换。支持日志修改/删除及重新算分。
4. **Phase 3：实用界面和长期稳定性。** 做满足用户操作体验的前端。Textual 是否符合“顺眼、直观”需要操作原型确认；跨 Windows/WSL 的 TUI 不是当然答案。连续运行之外，还要有故障注入与恢复证据。
5. **以后按实际需求扩展。** 第二个竞赛验证抽象，第二个键控器验证接口，之后再考虑 FT8/RTTY、解码融合、扫频和多智能体。单电台扫频会打断守听，Survey 需要明确接收资源和优先级。

三路解码“投票”应后移：不同路的延迟、文本切分及置信度不可直接比较，错误也可能相关。先测一条链路的呼号、交换字段完整正确率、假阳性及 p95/p99 响应时间；总体 CER 不能证明自动应答可靠。

删除“300–500 行编排器”“290 行引擎”作为实施预算。它们最多描述演示原型，未计持久化、恢复、认证、边界解析、日志更正、协议差异与运维。按可验收能力估算，比行数更可用。

## 五、需要收敛的设计决定

- 主日志真源选择，以及 TLF 是否只作可选校验器。
- 首版部署操作系统、设备唯一持有者和键控路线。
- 首版的批准单位：单条 CW 消息、有限次数 CQ 循环，还是单通 QSO；审批与取消的具体边界。
- 首版只覆盖 WAPC-CW 中国参赛台与日常 CW，是否符合当前目标。
- 前端形态是否接受 TUI；可以用原型评审，不影响离线核心准备。

这些是实施前的设计收敛项。现有“CLI 优先、不 fork、复用开源、N1MM 作可选只读来源”不需要重开讨论。
