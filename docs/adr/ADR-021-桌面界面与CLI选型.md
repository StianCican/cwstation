# ADR-021：桌面界面与CLI选型

日期：2026-10-20，2026-10-21补充。状态：用户已选择此技术方向；V00-04-A已完成最小演示壳和受限控制边界，尚未接真实会话、打包或跨平台验收。0.0整体仍未完成。

## 决定

2026-10-21视觉方向补充（用户明确）：多参考苹果设计语言，以Apple Human Interface Guidelines的清晰层级、适度留白、精细排版、克制材质、状态反馈和一致交互为参考。保持CW操作台的扫描效率、信息密度和风险状态可辨性；不照搬品牌资产，不用装饰性大卡片或营销页替代工作界面。优先浅色/中性材质、细分隔线、紧凑工具栏、分区和原生感控件；暗色模式应同样遵循层级。现有深色验证壳不是最终视觉基线。

此约束不改变Electron/React/TypeScript/Vite选型，不引入第二套状态或设备链；组件库/样式工具是实现手段，不能替代设计，也不因本条自动新增依赖。

- 桌面界面采用Electron + React + TypeScript；前端开发构建采用Vite。
- 提供CLI操作入口，复用现有命令行能力；GUI与CLI依赖同一应用控制逻辑、状态与记录，沿ADR-020既有设备链增量接入，不能各写一套收发流程或争用真实端口。
- 核心保持可在不启动Electron的情况下由CLI使用，避免终端操作依赖桌面环境。CLI指命令行操作；全屏交互TUI尚未确定，不自动增列第三种完整界面。
- 跨系统设计目标为保留Windows/Linux复用能力和macOS可迁移性；各系统的实际支持须分别验收，不承诺0.0自动包含三平台成品发布。

## 依据与代价

已有核心为TypeScript/Node，设备使用serialport；V00-04-A已用Electron/React/Vite实现演示壳。Electron便于复用现有Node能力，并适合Windows桌面交付。浏览器本地Web需额外确定后台部署及生命周期；Tauri需协调Rust和既有Node运行时，因此不改走这两条路线。

接受Electron包体和内存代价；serialport与Electron运行时兼容、音频设备接入、打包和实际跨平台行为均待验证。选择框架不等于上述问题已解决，不自行引入更多服务/协议作为前置条件。

## 待论证边界

界面布局、音频采集与CW解码、自动收发场景与权限、GUI/CLI协调和进程生命周期、界面故障/退出后的控制行为、发布系统及验收条件，继续在V00-01逐项论证。界面不直接打开串口，AI不直接获取设备或批准权限；具体进程/通信设计尚未决定。
