## 已确定的最小设计

1. 原执行记录保留 unknown，不改为 completed/cancelled。增加 ExecutionResolution 独立记录（proposalId 唯一、resolvedAt、operator、note、confirmedStopped=true，必要的契约版本）。schema 2 → 3 显式迁移，保留所有旧数据；兼容新增接口，RPC version 1 无破坏变化可保留。
2. 存储可查询 unresolved unknown（排除有 resolution 的 unknown），无任意 LIMIT；启动恢复只对未解除 unknown 阻止。提供核查记录查询。CLI `unresolved` 与 `resolve-unknown <proposalId> --operator <name> --note <reason> --confirm-stopped`；RPC 对应 unresolved、resolve-unknown。运行时确认字段必须严格 true，operator/note 必须非空并设长度上限；CLI 严格校验该命令旗标与多余参数。
3. 为避免仍在本进程运行的 FakeKeyer 迟到副作用，只有 recoverOnStartup 成功时已存在的 unresolved unknown 可解除；本次启动后新增 unknown 必须先停机重启。记录 eligible ID 集合，不靠墙钟判断。running、不存在、正常执行拒绝；同 ID 已成功解除的重试返回既有 resolution，绝不重复审计/改变 generation/解除其他故障。
4. 仅 fake-only 阶段支持此流程，文档说明同一 OS 用户的声明不证明真实人类或真实设备停止；将来真实后端必须设计核查步骤后才开放。必须无 active/txBusy、backendConnected，必须已恢复。
5. 不清除不相关存储故障。启动恢复时，保存允许解除的 unknown 阻止状态依据；本进程发生任意 intent/outcome/state 持久化故障后禁止解除（明确 fault latch，不能用随意字符串匹配绕过）。不能通过 resolution 清除数据库写入失败造成的 blocked。
6. 一次事务：插入 resolution、撤销全部开放授权和提案、generation+1、更新 blockedReason（仍有 unresolved 时保持 blocked）、追加 audit tx.unknown_resolved。内存态仅在提交后更新；写失败回滚 resolution/audit/generation，保持 blocked。必须处理多条 unresolved：逐条核查，最后一条才解除 unknown 阻止。禁止自动重发或自动批准；原提案重试仍返回原 unknown 结果。
7. `status/doctor` 暴露未解除计数及重启核查限制；更新 README 用法与已知限制，不建议手改数据库。
