## 用户可见增量与主链

```bash
node dist/apps/cwrig.js receive --decoder <executable> --pcm-s16le <file|-> \
  [--timeout-ms <1..3600000>]
```

- 主链：`apps/cwrig.ts receive → apps/rig-receive.ts → packages/receive/src/multimon.ts
  → 一个 multimon-ng 子进程`。发送仍沿 ADR-020，未调用、未修改发报链。
- 输入：22050 Hz、mono、signed-16 little-endian PCM 字节流；`-` 为 stdin。
  不改 WAV、不加声卡驱动/转换服务；验收时仍用已有 ffmpeg 转换。
- 正常输入 EOF 且无半个采样时补 0.5 s（22050 字节）零值静音，随后关闭引擎
  stdin；取消/失败不补静音。跨块奇数字节拼齐，最终残片明确失败。
- 进程：`shell:false`、`windowsHide:true`、固定参数
  `-q -c -a MORSE_CW -t raw -`；无任意解码器参数、无重启/重试。
- 输出：stdout 流式 UTF-8（跨块不丢字符），总字节上限默认 1 MiB；stderr
  持续读取但最多保留 64 KiB，不回显原文。文本回调串行 `await`，回调抛错终止。
- 事件：`source:"multimon-ng"`、`readOnly:true`、`sessionId`、仅非空文本递增的
  `seq`、`text`、本机 `receivedAt`。不保证每块是完整字符/词/报文。
- 取消：`SIGINT`/`SIGTERM`/外部 Abort 后丢弃迟到文本，销毁拥有的输入源，
  SIGTERM 后最多等 500 ms，必要时 SIGKILL；等待与清理有界。预先取消不 spawn。
- 退出码：正常完成 0；确认清理的主动取消 0；运行/清理失败 1；usage 2。
  无文本时 `state:"completed"`、`decoded:false`、`empty:true`，不虚报解码成功。

## 失败与修正（保留）

1. 流式用例首次失败：预期 3 个文本块，实际 2 个（`[1,2]`）。原因是测试自身把
   “收”的字节分片与后续 `" TEST"`/总字节写在相邻 timer 中，管道将其合并，不是
   产品丢字。把三个写事件拉开（20/80/140 ms）并断言拼接结果不含 U+FFFD。
2. 随后输出 `攋` 而非 `收`：测试夹具把 UTF-8 第三字节写成 `0x8b`，正确为
   `0xb6`（`收` = E6 94 B6）。修正夹具后同一断言通过；这是测试数据错误，
   不是解码实现问题。
3. 失败/取消路径的 `feedTask` 等待上限为 1 s，导致相关用例耗时约 1.3–1.9 s；
   这是有界清理成本，未以缩短等待掩盖。
4. 收尾自查发现总超时触发后主流程仍 `await` 文本回调链：回调永不结束会让会话
   永不返回，违反“等待有界”。加入 fail/abort 的停止信号并 race 子进程关闭、
   回调链等待；新增“回调永不结束仍按 120 ms 超时返回”用例。修正后 21/21，
   再执行最终 build exit 0。

以上修正均保留在测试与实现中，最终 21/21；没有为绿色放宽产品断言。

  复用同一源，契约只规定本会话拥有并使用一次。
