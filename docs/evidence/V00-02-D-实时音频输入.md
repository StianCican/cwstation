# V00-02-D 实时音频输入：实施、R01-R13 自查与专项证据

2026-10-21。结论：在既有 `cwrig receive` 上增加了一个 FFmpeg 采集子进程，
其 stdout PCM 按背压交给**同一个** `runMultimonReceive`。PCM 文件/stdin 模式
保持原路径与输出语义；实时模式只增加一个会话内采集进程，没有新增解码器、
CLI/服务入口、协议、持久化格式或设备持有者。Node 夹具专项覆盖固定参数、
模式互斥、背压、缺失/提前退出、双向失败清理、预取消、超时/SIGKILL、回调
挂起和确认清理。Codex已完成真实Linux/WSLg monitor采集验收：编译CLI完整解出CQ TEST，主动停止exit0。Windows原生、物理麦克风和电台未验。下文DSH交接时的“真实采集未验”以文末更新替代。

## 用户可见增量与主链

```bash
# 原 PCM 模式，行为不变
node dist/apps/cwrig.js receive --decoder <multimon-ng> --pcm-s16le <file|->

# 新增实时音频模式；二选一，不能同时给出
node dist/apps/cwrig.js receive --decoder <multimon-ng> \
  --ffmpeg <ffmpeg> --audio-backend <pulse|dshow> --audio-device <name> \
  [--timeout-ms <1..3600000>]
```

- 主链：`apps/cwrig.ts receive → apps/rig-receive.ts → packages/receive/src/audio.ts
  → 一个 FFmpeg 采集进程 → 同一个 packages/receive/src/multimon.ts
  → 一个 multimon-ng 进程`。发送仍沿 ADR-020，未调用/修改发报链。
- 输入：显式设备，固定转成 22050 Hz / mono / signed-16 little-endian。不采集
  默认麦克风，不接受任意 FFmpeg 参数、shell 或网络输入，不保存原始音频。
- 进程：`shell:false`、`windowsHide:true`；采集器 argv 由
  `buildFfmpegCaptureArgs` 固定，dshow 设备作为单个 `audio=<name>` argv 传入。
  平台匹配默认按 `process.platform` 在共享 wrapper 内强制；仅测试/嵌入可注入
  平台，CLI 不暴露该覆盖。
- 输出：文本 chunk 仍为 `source:"multimon-ng"`、固定 `seq`/`receivedAt`；实时
  状态额外报告 `audioBackend`、`audioDevice`、`audioSampleRateHz`、
  `audioChannels`、`audioSampleFormat`、`pcmBytes` 和有界采集 stderr 保留量。
  `pcmBytes` 只是交给解码器的字节数，不代表抄收成功或空口准确率。
- 退出码沿用：正常完成 0、两侧清理都确认的主动取消 0、运行/清理失败 1、
  usage 2。实时采集自然退出（包括 0）是 `capture_failed`，不会返回 0。

## DSH 实现检查项

下表沿用DSH交接原稿编号，其中R01-R13是其自定义实现检查项，未对应任务自查规范的原编号；正式规范映射以文末Codex复核为准。下文“真实采集未验”是DSH交接时状态。

| 编号 | 检查点 | 结论与证据 |
|---|---|---|
| R01 | 复用同一收报主链，不另写解码器/CLI/服务 | 通过。`runAudioReceive` 直接调用 `runMultimonReceive`；只新增一个会话内采集子进程。无第二套文本事件、存储或设备路径。 |
| R02 | CLI 必须显式二选一，参数在 spawn 前校验 | 通过。`parseReceiveArgs` 拒绝同时给 PCM 与音频、只给部分音频参数、非法 backend、重复参数、缺 decoder；测试覆盖且确认夹具未被 spawn。 |
| R03 | FFmpeg argv 固定、无视频/任意参数/shell；dshow 单 argv；平台匹配 | 通过。纯 builder 测试 pulse/dshow 全 argv 与 `audio=` 前缀；`audioBackendMatchesPlatform` 测试 Linux/Windows 正反例；dshow 在 Linux 解析器仍可用，实际 wrapper 需注入 win32 才执行。 |
| R04 | 预取消不启动任何进程/源 | 通过。API 在 spawn 前检查 `signal.aborted`；CLI 也会先返回 stopped。测试确认 FFmpeg 与 decoder 的 argv 日志都不存在。 |
| R05 | FFmpeg 缺失与一般采集失败区分 | 通过。等待 `spawn/error` 后再启动 decoder；ENOENT 映射 `capture_missing`，测试确认 decoder 未启动；其他 spawn 错误/输出错误为 `capture_failed`。 |
| R06 | 实时采集自然退出（含 0）不得伪装完成 | 通过。exit/end/error 任一发生即记录 `capture_failed` 并取消 decoder；测试分别覆盖 exit 0 与 exit 2，错误码不是 `aborted`。 |
| R07 | 采集失败取消解码；解码失败/回调失败取消采集 | 通过。采集失败经共享 AbortController 中止 decoder；decoder 错误后 finally 必有界清理采集。测试覆盖 capture 提前退出后 decoder 收到 SIGTERM，以及 decoder exit(4) 后 FFmpeg 收到 SIGTERM。 |
| R08 | 总预算从会话开始覆盖采集启动、PCM 和解码 | 通过。deadline 在 spawn 前计算；timer 在采集启动路径设置；传给 multimon 的是剩余预算；decoder 启动前再检查 deadline。超时测试同时覆盖启动等待和运行期。 |
| R09 | PCM 背压与有界计数，不无界缓存/不写音频 | 通过。源实现为对采集 stdout 的 async iterator，逐个 `yield` 并由既有输入写入 await 背压；测试用 4 MiB 快速输出 + 暂停读取的 decoder，确认 250 ms 后已交付 PCM < 1 MiB。无音频文件写入。 |
| R10 | 采集 stderr 持续排空、最多保留 64 KiB、不回显 | 通过。stderr data 持续消费并保留尾部；测试写入 100000 字节 stderr，确认错误对象报告 65536 字节且错误消息不含长串原文。 |
| R11 | SIGTERM 500 ms → SIGKILL 500 ms、无重试、清理失败非零、先清理后返回 | 通过。采集清理与 decoder 清理均用 500 ms 有界等待；两个顽固子进程测试确认 SIGTERM 宽限后升级且总时长短于 5 s。CLI 对 `cleanupConfirmed:false` 的取消返回 1；`runReceive` 在 `runAudioReceive` 完成两侧清理后才返回。 |
| R12 | 外部取消/回调挂起/迟到文本与失败优先级 | 通过。外部 abort 记录 `aborted` 并中止两侧；采集已先失败时保留 `capture_failed`，不吞成 `aborted`；永不 resolve 的 `onChunk` 由共享 timeout 中止并在 3 s 内返回。测试确认取消后只剩取消前文本。 |
| R13 | API 可用于未来 GUI、元数据/字节计数、PCM 兼容与边界 | 通过。`runAudioReceive` 接收 decoder/ffmpeg/backend/device/sessionId/onChunk/timeout/signal，返回音频元数据、`pcmBytes` 和 decoder 统计；PCM 旧 CLI 专项 5/5 通过。实时真实采集、Windows 原生、噪声/电台仍未验证。 |

## 限制与回退

- 实时会话的自然结束路径按“采集意外退出”失败处理；正常用户停止是 `SIGINT`/
  `SIGTERM`/外部 abort，只有两侧清理确认才退出 0。FFmpeg 若因设备消失自行
  退出，会得到 `capture_failed`，不会拿空文本冒充完成。
- `pcmBytes` 是交给解码器的字节数，可能因取消时的在途数据而小于采集器实际
  产生量；它不是抄收成功、信噪比或准确率证明。
- 采集 stderr 只保留尾部字节数，不提供原文；诊断时不能假设能看到 FFmpeg 的
  完整错误文本。
- 回退为恢复本轮 `audio.ts`、index、`rig-receive.ts`、`cwrig.ts`、README、
  新测试和本证据的修改前副本，并重新 build；不覆盖其他 dirty 变更或用户数据。
