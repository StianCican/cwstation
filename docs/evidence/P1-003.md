## 结论摘要

1. **进程 token default DACL 方案已证伪**：Node/libuv 用 `CreateNamedPipeW(..., lpSecurityAttributes = NULL)` 创建管道，得到的不是进程 token 的 default DACL，而是 Windows 固定的命名管道默认 DACL，因此“在 listen 前给当前 token 设置限制性 default DACL 让管道继承”不成立。
2. **同名实例共享 ACL 已独立证实**：同一管道名的多个实例共用同一个安全描述符；对任一实例调用 `SetSecurityInfo` 后，其它已存在实例以及之后新建的实例都读到收紧后的 DACL。
3. **“创建后收紧 DACL”不是安全边界**：访问检查发生在句柄**打开时**。在 listen 成功后、收紧前已经打开的句柄不会因随后 `SetSecurityInfo` 而被撤销，仍保有其打开时获得的访问权。用“RPC gate + grace 等待”无法证明不存在早已持有可用句柄的客户端，因此该 fallback 被禁止继续实现。
4. **备选（未实现）**：在创建时通过 Win32 `CreateNamedPipe` 的 `SECURITY_ATTRIBUTES` 指定限制性 DACL，并在 `dwPipeMode` 中加 `PIPE_REJECT_REMOTE_CLIENTS`。Node 公开监听接口未提供这些参数。最小桥接建议见 `docs/design/windows-pipe-creation-security.md`，待确认新增进程边界。

## 实验方法与实测结论

### 1. token default DACL（已证伪）

- 方法：`pipe-exp.mjs setdacl` 先经 `windows-pipe-dacl.ps1` 改 Node daemon 进程 token 的 default DACL，再 `server.listen(pipe)`，然后用 `scripts/windows-pipe-acl.ps1` 读实际管道 DACL。`dacl-exp.ps1` 增加对照：改 token 后分别创建 NULL SD 的事件对象与 NULL SD 的管道，比较两者读回的安全描述符。
- 结论：普通内核对象会随 token default DACL 收紧，而 `CreateNamedPipeW(..., NULL)` 创建的命名管道**不跟随**；管道仍是 Windows 命名管道默认 DACL（本开发机 P1-002 实测：`D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;OWNER)(A;;FR;;;WD)(A;;FR;;;AN)`）。因此无法靠改 token default DACL 获得“仅当前用户 + SYSTEM”。
- Codex 独立重跑 `node.exe logs/p1-003-exp/pipe-exp.mjs setdacl`：Windows Node v24.16.0，退出码 0。token 已变为 NETWORK deny、用户/SYSTEM allow；实际管道仍含 Administrators FA、Everyone FR、Anonymous FR。普通事件对象对照未在此次审查重跑。

### 2. 同名实例共享 ACL（已独立证实）

- 方法：`dacl-multi.ps1` 用 `CreateNamedPipeW`（NULL SD、`FILE_FLAG_FIRST_PIPE_INSTANCE` 仅首个）建 A–D；只对 A 调 `SetSecurityInfo` 收紧；读回 A–D；再新建 E 并读回。
- 结论：收紧 A 后 B–D 读到同一收紧 DACL，新建 E 也继承该 DACL。即一个管道名共用一个安全描述符，创建后收紧对后续 libuv 新建实例同样生效。
- 意义：这解释了为什么“创建后收紧”在**后续实例**上看起来可行，也正因如此掩盖了第 3 条的窗口漏洞。

### 3. 创建后收紧的漏洞：已打开句柄不可撤销

- 收紧 DACL 不会撤销已经授予的句柄权限。普通其他用户在默认 ACL 下仅获读权限，不能据此声称他们可以发送命令；风险包括提前取得读句柄，以及可能使用同用户凭据的网络连接。本结论为权限和时序审查，网络攻击未实测复现。
- `run-restrict.mjs` 按此顺序（listen → restrict → probe → clients）量化该模式，但无法排除窗口内已建立的连接；探针只读 ACL，不发送任何控制 payload。
- 因此“收紧前用 gate 拒绝所有 RPC、并给一个 grace 等待期”不能构成安全证明：gate 只约束本守护进程的 RPC 派发，不能约束外部何时打开管道句柄。审查已明确**禁止继续实现该 fallback**。

## 讨论备选（未实现、未验收）

**创建时原生 Win32 属性**：通过 `SECURITY_ATTRIBUTES.lpSecurityDescriptor` 指定限制性 DACL，在 `dwPipeMode` 加 `PIPE_REJECT_REMOTE_CLIENTS`。要点：

- 安全描述符与拒绝远程标志在创建瞬间由内核应用，无“先默认 DACL 后收紧”的窗口；`PIPE_REJECT_REMOTE_CLIENTS` 直接拒绝远程 SMB 管道访问，而不仅依赖 DACL 推断。
- Node 当前路径使用 NULL 安全属性。直接交原始 Windows HANDLE 给 Node 的可行性未验证，不能当作已成立方案；桥接进程建议见设计文档。
- 需在实现前评估：与现有锁、端点规范化、停机路径、双重实例拒绝的集成；非管理员能否设置 protected DACL；以及是否仍需第二用户/远程实测。
- 本任务**不实现、不验收**该方案；交由 Codex 设计评审后另行立任务。
