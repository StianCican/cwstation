# V00-02-E：CW 解码质量诊断（未验收）

日期：2026-10-27。本文记录当前 multimon-ng 收报主链的缺口和研究证据，不表示解码已修复。

## 现场事实

用户在 7.00993 MHz 附近听到清晰 CW；GUI 已实际运行既有链路：

`Electron GUI → runReceive → FFmpeg/RDPSource → 一个 multimon-ng → ReplySession`

`.local-backups/20261027-cw-quality/radio-15s.s16le` 是现场 PCM，约 14.987 秒，主峰约 530 Hz，SNR 约 13.5 dB。包络测量出现约 61..71 ms 点、188..193 ms 划。默认解码输出为：

```text
T N II T N RGER73<SK> E E E
```

其中没有已知人工电文作真值，因此只能判定为“有输出但不可靠”。

## 研究结论

- REA 对本机 fldigi 的静态源码/字符串/xref/decompile 证据显示，常用 CW 解码器会采用目标频率混频、窄带/匹配滤波、AGC/噪声底、迟滞和自动码速跟踪。REA Evidence：`ev_f952...`、`ev_cdaca...`、`ev_03cc...`、`ev_3bc...`。这是设计参考，不是本项目运行验收。
- DSH 定向审查记录于 `.local-backups/20261027-decoder-fix/dsh-research.log`。现有 multimon-ng `demod_morse.c` 只对全音频做整流包络；`AUTO_THRESHOLD_MULT=2/3` 绑定缓慢衰减的全局峰值，初始 `SQUELCH=500` 没有噪声底和迟滞。现场弱点划可能低于全局门限，开头静音也可能触发伪点划。
- `-o` 是 CW 幅度门限，不是音调频率；`-x` 才关闭自动门限，`-y` 才关闭自动时序。对同一现场样本，`-x -o 2600 -d 65 -g 65 -y` 只得到 `RGES73<SK> E E E`；门限继续升高会丢失输出。该候选不接入产品。
- 已有 440..620 Hz 带通未明显改善；噪声与 CW 能量同带，不能靠新增 FFmpeg 滤波链绕过解码器问题。

## 已实施的原地修正

在 multimon-ng 1.6.2 工作树内修改 `demod_morse.c` 与 `multimon.h`：自动门限模式加入噪声底跟踪、40%/28% 开关双门限迟滞、最低信号裕量 400，并将峰值衰减从 `999/1000` 调整为 `995/1000`；固定门限模式仍保持原有 `-x/-o` 语义。补丁副本：`.local-backups/20261027-decoder-fix/multimon-threshold-hysteresis.patch`。

构建与回归：

- multimon-ng 构建通过，CTest 5/5 通过。
- `clean.wav`、`noisy.wav` 与 `cq-test.s16le + 0.5 s 静音` 均完整输出 `CQ TEST`。
- 现场录音输出为 `T N T TE RGE A73<SK> E E E`，统计 `GLITCHES=0, FAILED=0, DECODED=15`。这是算法指标改善，不是人工真值验收。

## 当前修正边界

后续只允许继续修改同一个 multimon-ng 解码器实现；不新增第二个解码器、第二个采集进程、GUI、协议、存储格式或自动发射入口。真实现场验证前不宣称可靠抄收，也不因片段输出授权发送。

最小验收：

1. 同一现场样本的伪字符和明显错码下降，并保留原始输出作对照；没有人工真值时只称“改善”。
2. 既有 `cq-test.s16le` 仍能输出 `CQ TEST`。
3. 产品仍只有一个 `runReceive → multimon-ng` 主链，停止/清理行为不变。
4. 真实电台只做接收验证；不因解码片段自动授权发送。

在上述证据通过前，固定参数档、fldigi完整应用/XML-RPC、第二套自研解码器均保持冻结。
