## 2. 设计落地对照

| 任务要点 | 实现 |
|---|---|
| 原执行保留 unknown，新增独立核查记录 | `execution_resolutions` 独立表；从不 `UPDATE executions.status`；`proposalId` 主键唯一 |
| schema 2 → 3 显式迁移、保留旧数据 | `migrationV3` 只 `CREATE TABLE IF NOT EXISTS`；v1/v2 数据由既有迁移保留；未来版本仍拒绝 |
| 未解除查询无任意 LIMIT | `findUnresolvedUnknowns` 用 `LEFT JOIN execution_resolutions` 过滤，无 LIMIT，按 `started_at` 升序 |
| 重启恢复只对未解除 unknown 阻止 | `recoverOnStartup` 改用 `findUnresolvedUnknowns`；已核查记录不再阻止 |
| CLI/RPC 命令与严格校验 | `unresolved`、`resolve-unknown`；`confirmStopped === true`，operator/note 非空且有上限，CLI 拒绝未知旗标/多余参数 |
| 只允许启动时已存在的 unknown 解除 | `eligibleUnknownIds` 在恢复事务后一次性捕获，不靠墙钟；本进程新增 unknown 报 conflict 要求重启 |
| 幂等重试 | 先查 `getResolution`，存在即原样返回，不写审计、不改 generation |
| 无 active/txBusy、需连接、需已恢复 | 依次检查 `active`/`txBusy`、`backendConnected`、`recovered` |
| 显式故障闩锁 | `faultLatch` 在 intent/outcome/state/授权失效/关闭/解除写失败时置位；解除直接拒绝，无字符串匹配绕过 |
| 单事务解除 | 插入 resolution、撤销全部批准、终止开放提案、generation+1、重算 blockedReason、追加 `tx.unknown_resolved`；提交后才改内存 |
| 多条逐条核查 | 每次只插入一条 resolution；仍有未解除时按剩余列表重写 blockedReason；最后一条才回到无 unknown 阻止 |
| 原提案不重键、不自动重发/批准 | `transmit` 遇已存在执行直接返回原结果；解除不改写执行；新发射需重新提案并单独批准 |

## 4. 关键场景的实际输出

以下为使用 `dist` 手工演示（临时目录/数据库，结束后清理）的真实输出。

SIGKILL 掉正在发射的 daemon 后，用同一数据库重启，`status` 显示阻止依据：

```json
{"ok":true,"method":"status","result":{
  "generation":1,
  "blockedReason":"unresolved unknown execution e3dc6152-... (started 2026-10-05T10:28:07.794Z); operator review required before further transmit",
  "executionCounts":{"unknown":1},
  "approvalCounts":{"active":0,"consumed":1,"revoked":1},
  "schemaVersion":3,
  "unknownReview":{"unresolvedUnknownCount":1,"eligibleToResolve":1,"requiresRestart":0,"faultLatched":false,"recovered":true}
}}
```

`unresolved` 列出可解除项与重启限制：

```json
{"ok":true,"method":"unresolved","result":{
  "unknownReview":{"unresolvedUnknownCount":1,"eligibleToResolve":1,"requiresRestart":0,"faultLatched":false,"recovered":true},
  "unresolved":[{"proposalId":"0e010034-...","status":"unknown","detail":"daemon restarted while execution was in flight; stop cannot be confirmed","resolutionEligible":true}],
  "resolutions":[]
}}
```

`resolve-unknown` 成功写入独立核查记录：

```json
{"ok":true,"method":"resolve-unknown","result":{
  "proposalId":"0e010034-...","contractVersion":1,
  "resolvedAt":"2026-10-05T10:28:00.975Z",
  "operator":"alice","note":"checked, radio stopped","confirmedStopped":true
}}
```

解除后 `status` 不再阻止，原执行仍为 unknown，generation 递增：

```json
{"ok":true,"method":"status","result":{
  "generation":2,"blockedReason":null,
  "executionCounts":{"unknown":1},
  "unknownReview":{"unresolvedUnknownCount":0,"eligibleToResolve":0,"requiresRestart":0,"faultLatched":false,"recovered":true}
}}
```

原提案重试返回原 unknown，不重新键控：

```json
{"ok":true,"method":"transmit","result":{
  "proposalId":"0e010034-...","status":"unknown",
  "detail":"daemon restarted while execution was in flight; stop cannot be confirmed"
}}
```

CLI 严格校验与退出码（手工）：

```

{"ok":false,"code":"usage","error":"--confirm-stopped is required"}   exit=2

$ cwctl resolve-unknown does-not-exist --operator alice --note checked --confirm-stopped
```

## 5. 测试覆盖清单（新增用例）

| 验收项 | 用例名 |
|---|---|
| 缺确认/空 operator/note/超长/非法参数 | `resolve-unknown rejects missing confirmation, empty fields and over-length input` |
| 不存在/非 unknown/running | `resolve-unknown rejects nonexistent, non-unknown and running executions` |
| 本次进程 unknown 不能解除 | `an unknown created after startup recovery requires a restart` |
| 重启后解除、撤销旧授权、原执行不重键、需重新批准 | `resolve after restart unblocks, revokes old authorizations and never re-keys` |
| 重试幂等 | `repeating resolve returns the existing resolution without extra audit or generation change` |
| 多条部分解除仍 blocked，最后一条解除 | `multiple unknowns stay blocked until the last one is resolved` |
| 重启后已解除不再次 blocked | `a resolved unknown does not block again after restart` |
| 解除写失败原子回滚、仍 blocked | `resolve write failure rolls back atomically and keeps the station blocked` |
| 其他存储故障不能清除 | `a persistence fault latches and resolve-unknown refuses to clear it` |
| 需已恢复、需后端连接 | `resolve-unknown requires completed recovery and a connected backend` |
| 跨进程崩溃→重启→RPC/CLI 解除→再授权 | `cross-process crash, restart, resolve and re-authorize via RPC and CLI` |
| CLI 严格旗标与退出码 | `CLI resolve-unknown strictly validates flags and maps semantic exit codes` |
| schema v2→v3 保留执行与审计 | `v2 database with executions and audit migrates to v3 without data loss` |
| 未解除查询排除已核查、无 LIMIT | `unresolved unknown query excludes resolved and includes every unresolved row` |

## 7. 已知限制与未决项

- 仅 `FakeKeyer`，未接真实电台、未做真机验证。
- 核查解除只处理启动恢复完成时已存在的 unknown；本进程新增 unknown 必须停机重启。这是为避免本进程 FakeKeyer 迟到副作用与解除后的新操作交错。
- `--confirm-stopped` 是同一 OS 用户的操作人声明，不证明真人参与，也不证明真实设备停止。真实设备核查步骤在 Phase 1 设计，不直接复用离线声明作为物理停发证明。
- 本进程发生 intent/outcome/state/授权失效/关闭/解除持久化故障会闩锁解除路径；闩锁是进程内的，重启后可重试，但持久化故障是否仍存在需人工确认。
- 下述 Codex 最终审查纠正了“非 unknown 的持久阻止原因不可达”的假设：状态重试等后续成功写入确实可以保存故障阻止原因。
- TTL 仍使用系统墙钟，时钟跳变处理待完善（沿用 P0-002 状态）。
- 锁 guard 异常残留仍需人工处理（沿用 P0-002 状态）。

## 8. Codex 审查补充

DSH 交回 P0-003 后，Codex 补上两处限制：非 Fake 的 daemon 拒绝 `resolve-unknown`；存储故障使用独立 `storage_fault` 字段持久化，schema 3→4 显式迁移。v1/v2/v3 数据保留，未来版本继续拒绝。旧库无法识别的阻止原因保守保留为故障，不因核查 unknown 清除。

增加测试：故障与 unknown 并存时重启仍拒绝解除、非 Fake 拒绝离线解除、v3 核查记录迁移保留、旧 v3 不相关阻止迁移保留。独立运行 journal 测试 10/10 通过、journal+resolution 测试（最后一项迁移用例加入前）23/23 通过，构建通过。最终全量结果在本轮结束时追加。

持久存储故障没有自动解除命令，需要后续单独设计修复与核查流程；本功能只解除 unknown。数据库完全不可写时，独立故障记录也可能失败，仍保持本进程阻止，不能承诺错误一定落盘。
