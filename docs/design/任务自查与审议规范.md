## 主轴检查（任务启动和范围变化前）

2026-10-20复用调查经验：先查项目既有能力，再查成熟软件公开接口/源码，确需安装包或运行证据才用REA。优先外部调用和薄适配，不因参考软件而重建已有Fake/设备会话。软件队列事件、状态广播、命令应答和物理结果分别判断；研究一旦足以支持当前接入就停止扩大。单消费者接口由共同核心读取，GUI/CLI不各读一套；建议只有实际接入调用者后才能记为交付。复用证据与下一项受影响行为检查，不复制全套测试矩阵。

在现有任务单中填写以下六项，不另建任务管理平台：

1. 用户可观察的主链缺口及本项完成条件。
2. 既有调用路径、复用模块和唯一修改负责人。
3. 最小原地修改范围，以及明确不做的内容。
4. 入口/进程/协议/记录格式的本次增减；不变也须说明。
5. 若为替换：旧调用者迁移、切换验证、兼容/冻结、数据保护及回退；不涉及替换写明不适用。
6. 与风险匹配的验收方法、保护基线和交接状态。

当前设备功能主链以AGENTS和ADR-020为准。缺少主链位置或仅以未来扩展性证明新增路径时，不进入实施；先提交证据和最小替代方案。新链通过自己的测试而旧调用者未迁移，只能记为候选实现，不能记为统一完成。离线模拟优先注入主链既有transport，不另建生产候选会话。

## 职责与状态

Codex负责设计、任务边界、成果复核和最终验收；DSH负责实施、自查、审议报告和可复现证据。DSH可以审议自己的成果，但必须标明自查，不代替Codex复核。DSH审议Codex成果时标明交叉审议。

任务状态依次为：已委派、执行中、待审议、修正中、待复核、已验收。提出设计、写完代码、构建成功和DSH自报完成都不能直接标为已验收。设计草案须通过设计审议才能作为实现基线；设备验收与离线验收分开记录。

## 必须执行的检查点

1. 开始前：读取AGENTS.md、MEMORY.md当前事实清单、相关ADR和任务，按已完成项与证据排重；确认授权、真源、修改权与备份基线。回答下一步或委派前同样须核对，复验必须有受影响变化、证据缺口或回归依据。基线范围须覆盖验证工具的持久化输出（例如logs、dist、诊断文件和数据库），不能只备份源码；临时目录与新增文件须明确其创建前不存在。
2. 设计定稿前：核对接口、状态转换、失败处理、依赖方向、兼容性及验收方法。
3. 第一条可运行链路完成后：核对实际行为与设计，检查模块边界、输出语义和资源生命周期。
4. 范围或接口改变时：在继续扩大修改前检查依据；重大架构/公共接口变化交Codex裁决，必要时由用户决定。局部修正按既定授权推进。
5. 接入外部服务、持久化数据或真实设备前：核对权限、数据流、失败后恢复和本次验收授权；离线证据不能替代真实设备证据。
6. 每项任务交付前：检查最终差异、验收证据、残留进程、文档和记忆一致性，更新当前事实清单的完成范围/证据/限制/未完成状态；用户纠正后先修清单再继续规划。修正后复核受影响部分。

这些检查由事件触发，不按固定代码行数或时间机械执行。跨多个阶段的任务必须在报告中逐项记录检查点，不得只在最后补一句“已自查”。

## 最小必要验证（2026-10-20用户要求）

- 历史有效证据默认复用。开始验证前写明本次受影响行为及最小用例；换会话、换审阅者或“本轮没跑”不是重测理由。
- 只读分析/文档更新只核对相关内容与差异，不运行产品测试、构建或实机验证。局部代码修改只跑受影响用例；涉及共享接口时扩大到直接调用者，不默认全仓、多平台、源码和编译版全部重跑。
- 同一最终版本和环境的一份可复现证据可供DSH自测与Codex复核共享。Codex检查对象、结果和限制，有证据不足或行为疑点才复现对应项，不机械复制整个测试矩阵。
- 必要的设计/交付审议保留，但小修复合并检查，修正后仅复核差异；无新变化或发现不反复审议。已有验证一旦满足该交付条件即继续推进。
- 实机验证只补本次新增/改变的硬件行为及仍缺失的整体验收，不反复重做已通过的只读/预检。真实发射、停止、数据兼容等关键行为改变仍须对应验证，不能因减负而跳过。
- 通常在实际调用链首次接通及版本交付时做整合验证；其间仅有新修改、失败、明确疑点或用户要求才重复。验证不另外建设平台或制造新前置任务。

## 审议标准

| 编号 | 标准 | 必需证据 |
|---|---|---|
| R01 | 符合用户目标、授权及任务范围 | 要求到实现/文档的对应表，未完成项和范围变化 |
| R02 | 符合项目ADR、模块边界和真源约定 | 依赖与调用路径，偏离条款及原因 |
| R03 | 公共协议、配置、存储和更新可维护 | 版本/兼容策略、迁移及回滚依据；无变化时注明不适用 |
| R04 | 输入和外部结果在运行时校验 | 类型、长度、未知字段、错误响应、资源上限的处理依据 |
| R05 | 发射许可和设备所有权明确 | 唯一持有者、一次性授权、上下文绑定、重复/重启行为 |
| R06 | 停止、超时、断线和未知状态语义可信 | 不把命令写出或OK当成停止/完成证明；不得自动重发 |
| R07 | IPC与并发失败有界 | 请求关联、执行后丢回执、迟到回复、重复请求、服务重启、急停调度 |
| R08 | 权限声明与实际隔离一致 | token/通道权限依据；同用户进程能力与AI可访问范围 |
| R09 | 资源及持久化失败可恢复 | timer/listener/端口/进程清理、写入失败、备份和恢复 |
| R10 | 验证与风险匹配 | 实际命令、退出码、环境、结果及未覆盖项；不编造通过 |
| R11 | 修改受保护且范围可复核 | Git基线或修改前文件备份位置、最终diff/比较结果 |
| R12 | 状态、文档和证据准确 | 草案/实现/离线验收/实机验收分开，避免过期描述误导 |
| R13 | 主轴连续且没有未说明的并行建设 | 主链调用位置、复用依据、入口/进程/协议/记录格式增减；替换需旧调用者迁移与切换证据；被替代文档状态已同步 |

每项必须标为通过、问题、未验证或不适用；不适用须说明原因。规范冲突须列出具体来源并升级，不自行忽略。阶段自查不意味着每次都运行全套测试；按实际变更执行必要检查，已有有效证据可引用。

## 严重程度和通过条件

- S0：可能产生未经授权发射、错误停止声明、丢失用户数据或泄露凭据。立即停止相关执行，保留现场。
- S1：违反关键接口/所有权/恢复契约，或核心行为无法正确验收。阻止进入后续相关阶段。
- S2：局部功能、兼容性、证据或文档缺陷。验收前修正；确需保留时由Codex记录理由、影响、负责人和后续任务，不隐藏问题。
- S3：维护性建议，无当前行为错误。可记录后续处理。

没有未解决的S0/S1，所有验收条款有证据或明确限制，S2有修正或明确处置，才能提交“建议通过”。最终验收由Codex复核。未验证的关键条件阻止对应范围通过，不能将未验证写成没有问题。

## 偏离处理

发现偏离时记录：要求来源、期望行为、实际行为、触发场景、文件/行号、影响、修正建议。局部问题先修正，再检查最终diff并针对影响复验；扩大范围或改变已接受架构时先提交证据和备选方案。修改前保护规则同样适用于修正。

## 报告格式

每个任务报告保存在docs/evidence或docs/reviews，包含：任务编号/版本、审议对象版本或文件SHA-256、作者与审议者、检查点记录、R01-R13对应结果、按严重度排列的发现、验证证据、未覆盖风险、修正与复核记录、建议结论。现有文件必须先读、备份后才更新。历史R01-R12报告不追溯改写为已通过R13。

每个发现提供可定位依据，区分已证实缺陷和待确认假设。无发现时仍报告未验证范围。模拟结果不得推广为真实电台、Windows/Linux或射频都通过。

不得预设审议必须找出问题或必须不通过。字段缺失、描述歧义和行为矛盾分别说明；严重度按具体影响确定，不用假定的错误实现替代现有设计事实。Codex可以对DSH建议作有依据的不同裁决，并在独立复核记录中说明。
