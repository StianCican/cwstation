# Windows 管道创建权限：P1-003 替代方案

- 日期：2026-10-06
- 状态：用户已同意实施方向；P1-003-v2/ADR0006已实现并通过开发机离线验收，发布环境未验收。实际范围以docs/evidence/P1-003-v2.md为准。
- 依据：`docs/evidence/P1-003.md`；不授权 USB 接入或发射。

## 已证实的问题

原生 Windows Node 24.16.0 创建命名管道时没有采用已修改的进程 token
默认 DACL。创建后替换 DACL 会同时约束已有及新建实例，但不能撤销先前已
打开句柄的访问权。RPC 就绪门和固定等待时间不能证明所有旧连接都已排除。

不能交付该路径并声明已实现同用户隔离。Linux Unix socket 路线保持现有实现。

## 建议的最小调整

增加一个小型 Windows 专用管道桥接进程，由 daemon 启动和管理。桥接进程
通过 Win32 `CreateNamedPipeW` 创建、接受、读写和关闭管道；首次创建就传入
显式 `SECURITY_ATTRIBUTES`，不能先用默认权限创建再收紧。

- SID 从实际进程 token 获取，并核对与 daemon 的用户一致。
- 保护 DACL，仅允许当前用户与 SYSTEM；显式拒绝 NETWORK。
- 每次创建实例使用 `PIPE_REJECT_REMOTE_CLIENTS`；首次实例使用
  `FILE_FLAG_FIRST_PIPE_INSTANCE`，遇到同名服务拒绝启动。
- 读回实际安全描述符，检查 owner、DACL 和 ACE 后报告 ready。
- 对外继续使用当前命名管道地址及 NDJSON RPC，不修改协议版本、配置或数据库。
- 桥接进程只处理通信，没有授权、批准、恢复、设备或数据库权限逻辑。
  所有操作仍由 TypeScript 的同一 RPC 入口校验和执行。

优先评估 C#/.NET Framework 小程序，当前 Windows 已有编译器；不要求先安装
新 SDK。需先验证目标 Windows 的运行环境及可复现构建，再确定交付方式。
发布源码、构建命令和产物校验，不在每次启动临时编译。

## 新增边界与代价

daemon 与桥接进程使用继承的匿名 stdin/stdout 管道通信，不开放另一个
TCP 或默认权限命名管道。内部帧带连接编号，限定大小、队列、超时和连接数；
响应仅回到对应连接。内部通信格式单独版本化，stderr 只用于诊断。

增加一个子进程及内部通信适配，需要处理启动失败、崩溃、背压和孤儿进程。
桥接进程故障必须停止接单，并触发现有撤销授权和有界取消路径；daemon
退出时桥接进程关闭监听，且 daemon 意外退出后不得继续提供服务。
不能凭转发成功声称请求成功，也不能恢复时自动重发。

客户端的服务身份核验仍需纳入实现设计：创建侧的首次实例标志只保护 daemon
启动，不能单独证明 CLI 连接的服务可信。应检查服务进程身份及实际 token
用户，失败拒绝发送操作；具体 Win32 接口和边界在任务中明确。

## 验收条件

1. 在权限验收完成前不启动恢复、不提供 RPC、不报告 ready；任何失败关闭端点。
2. Windows 原生实测创建时 ACL、多连接与替换实例、同名抢占、初始化失败、
   桥接进程/daemon 崩溃及停机；检查无遗留服务。
3. 验证当前用户可访问、受限 token 被拒绝；明确区分 AccessCheck 推导与真实
   第二用户/远程登录测试，不能把未做测试写成已通过。
4. Windows 与 Linux 的 Fake 回归继续通过；核心发射状态机和公共 RPC 不变。

管理员提权及 SYSTEM 不属于对抗范围。同用户隔离不等于真实人类批准，
也不能阻止具备同用户 shell 权限的 AI 调用控制入口。
