## 3. 模块边界与设备持有者

现状：apps/rig-controld.ts只是委托rig-statusd的只读入口；apps/rig-faked.ts才是daemon启动的私有Fake控制子服务，两者没有在一个进程中实现统一后端。
拟扩展rig-controld承接真实串口的唯一持有者及私有受控入口；rig-faked保留独立模拟替身和v1入口，不迁入真实进程、不持有串口。具体真实启动参数另在B冻结，不把名称中的control当成现有发送能力。

| 进程/端点 | 现状 | 迁移后的职责（建议） |
|---|---|---|
| daemon | 核心授权及Fake子服务宿主 | 核心授权、真实服务私有会话宿主；不直接开串口 |
| rig-controld | rig-statusd只读委托 | 真实唯一持有者；同进程仲裁状态读取/受控写入 |
| rig-faked | 私有Fake服务、无串口 | 保留模拟测试入口；与真实服务互斥选择 |
| 公共状态端点 | 受保护status/watch | 只读投影；与私有控制通道分离，保留原状态/锁兼容 |
| 私有控制通道 | Fake继承stdin/stdout | 真实v2继承通道；不暴露在公共端点 |

daemon与设备服务仍分进程、分权限入口、分数据锁，符合ADR0007。统一发生在真实设备服务内部；不存在另一个写入进程打开同一串口。新服务stdout只承载私有协议，状态发布走原受保护端点，诊断不写入协议/密钥。

调用路径：CLI/界面/AI -> daemon TxController -> 真实专用Keyer客户端 -> 私有控制通道 -> 统一设备服务 -> 单串口仲裁器 -> IC-7300。
只读监视客户端通过受保护公共状态端点读统一设备服务；没有控制方法或raw.write。AI保持提案权限。

建议模块职责：

- packages/devices：CI-V编码/解码、窄transport和串口生命周期；仲裁器唯一接触transport，校验固定命令和载荷。
- packages/rig-control：通道校验、会话认证、设备账本、许可及业务operationId；真实后端独立于Fake实现，不继承模拟完成行为。
- packages/rig-status：兼容既有状态订阅与CLI视图；读不到TX字段时显示未知，不由RX推断。
- packages/core：提案、批准、执行与核心unknown。Julia只生成离线向量/分析，不访问设备或介入停机时限。

旧serial.ts的03/04白名单保留。受控transport单列实现，共用经核查的串口底层生命周期；不把旧只读入口改成通用write。新增读命令先提供准确手册依据及精确白名单，再纳入受控路径。
所谓共用是后续B评估提取open/set/flush/drain/close、超时及资源登记的内部机制，两个窄transport各持自己的不可放宽write策略；不是复用现有只读SerialTransport.write来写0x17。抽取前独立设计/审议保护边界，不为本轮提前重构。
移交顺序：禁新提案执行/撤销批准 -> 处理在途unknown -> 关闭旧rig-statusd并确认端口释放 -> 新服务独占开口 -> 发布新实例能力。失败不启动第二持有者。
回退亦先禁发、处理unknown、确认新服务关闭，再恢复旧只读服务；不得绕过账本或重放旧操作。rig.sh变更属于C，尚未实施。

## 4. 能力与版本方案（建议，待实施设计确认）

版本1的fake/simulation语义保持原样。建议真实通道使用严格版本2；上线前单独确认字段schema、配置版本和升级/回退方式。不在版本1添加未经旧校验器允许的字段，不提供自动降级。
旧Fake客户/服务继续v1；新真实客户/服务只接受v2。版本不匹配在任何intent/设备副作用前失败，不进行版本探测式发送。
v1硬边界为protocol.ts的版本/来源常量、literal类型/validateResponse、RemoteKeyer.checkDeviceContext；v2单列模块/验证器/真实Keyer，不就地放宽这些检查。核心及用户RPC的contractVersion/protocolVersion与设备IPC版本分别管理；上下文持久化变更须同时设计核心契约/schema升级。

v2候选能力字段：backendKind=ic7300、evidenceSource=device、readFrequency/readMode、可用TX上下文读取、cwSend/cwStop、completionEvidence/stopEvidence的类型及版本、设备/服务实例与各代次、blockedReason、maxMessageBytes=30、charsetVersion。
字段命名和编码仍是建议，不改变现有TS类型。首个真实只读版本cwSend/cwStop/ptt=false，完成/停止证据unavailable。methods不能宣告可执行cw.send/cw.stop。
仅证明命令可接受但未证明完成时，日常cwSend仍false。设备读取证据不等于simulation，Fake能力永远不能替真实后端证明。

| 现有表示 | v2映射规则（B冻结精确schema） |
|---|---|
| rig-control v1可靠完成/停止boolean | 保持模拟定义；不得直接复制为真实true |
| rig-status只读unavailable | 旧只读投影继续unavailable；有能力的新状态单列版本，不放宽旧approval-gate |
| v2证据类型/版本 | unavailable映射false；只有该设备证据路线已验收且当前可用才派生true；未知类型拒绝 |

真实keyedCount默认null，表示缺少实际键控次数证据，不由请求/FB/时间估算，也不回退0。真实诊断分别记录send请求次数、帧写尝试、命令应答和可靠终态；均不是射频实际发码次数。现有ExecutionMetrics.source固定simulation，不能复用它标记真实结果；新计数/来源类型及status兼容在B公共契约设计中冻结，E前验收。

控制会话沿用私有继承通道、宿主监督、有效会话认证和有界关闭；v2签名必须绑定协议版本、方法、设备/服务实例、内容hash、TX上下文摘要、各代次及期限。精确签名序列在v2专门设计中冻结，不与v1混用。
仍禁止raw.write/任意命令/任意端口参数RPC。只读端点不能取得控制密钥；同OS用户仍是信任边界，不能宣称抵抗同用户任意调试/文件修改。

## 5. preflight与批准绑定

真实设备标识基于明确配置及可核查硬件身份，不仅使用COM17。历史COM17/19200、0x94/0xE0是已记录配置，不代表当前连接/菜单真值。端口路径变化不能创建新身份以解除旧unknown。
服务实例每次启动变化；连接代次在失效/重建时变化；许可代次在stop/close/状态变化时撤销。核心stateGeneration继续由核心管理。

第一版候选可发送上下文限制为CW、simplex、split关闭、RIT/XIT关闭、无其他键控来源、已知选中VFO及TX频率。CW-R及复杂双VFO另验收，绝不把核心mode:CW视为设备实际CW。
必须调查/验证：实际模式、选中VFO、split、RIT/XIT、TX频率推导或直接读取、CW速度、BK-IN、已有TX/队列活动及控制线设置。字段读不到/语义不明则对应发送能力不成立；不要求软件自动修改菜单。

快照非原子：每字段带采样来源/时刻；发送前在仲裁器内重新采样关键上下文，比较批准指纹。拟要求两组一致观测且总采样跨度<=500ms、最新字段年龄<=500ms（候选参数，尚未真机测得）；失败即禁发，不能只更新时间戳。
期间不能插入其他服务写帧；检测到变化撤销批准。采样后面板仍可能变化，这是软件无法消除的竞态；稳定两次不是原子TX频率保证，C/D须确定操作约束及可接受范围，未解决前E不通过。

批准指纹应包括真实TX上下文和证据能力版本。现有Proposal只绑定文本/频率/核心mode，不能完整表示上述字段；v2需要设计显式上下文摘要及其持久化/批准绑定，不能仅存在客户端缓存。此公共契约改动另经确认后实施。
RF功率0仅是用户现场声明，不提供完成/停止证明。USB SEND、USB Keying(CW/RTTY) OFF、抑制定时器ON及独立停机准备属于现场清单；开口仍可能控制线跳变，软件不能承诺开口零副作用。

## 6. CI-V串口仲裁与无关联回执

只允许一个在途普通CI-V事务、一个业务CW操作。轮询和发送共用仲裁器，不同时读取同一串口；一帧不可交错。发送不自动分块，不因NG/超时/重连重发。
stop先在本地撤销许可、丢弃未写出的发送队列，再抢占轮询；等待当前帧有界完成或报错，不能交错插入FF。普通队列上限32、预留一个stop/close槽；同目标stop合并。
串口写/排空/普通应答各拟上限2秒，关闭2秒；队列等待与业务总deadline另设有界期限，不使用无限排队。停止延迟受当前帧写入期限约束，不能承诺即时硬件停止；这些参数必须经平台验证。

CI-V的FB/FA没有业务operationId，也不回显完整消息；唯一持有者和单事务只减少歧义。echo剔除与地址核验不能解决迟到FB归属。
首个候选只记录ack_observed（字节、地址、时刻、会话及当前事务候选），不据此赋值command_accepted。只有A建立可审议、可验证的正向关联依据后才允许使用command_accepted；唯一在途/flush/时间窗口单独都不足，无法建立则保留未关联诊断。
任何命令超时/异常/回执归属无法确定后会话失效并禁发，晚到FB仅存诊断；flush/重连不证明旧CW队列已清空。重连也不自动恢复许可。一次业务send在账本中只触发一次CW帧写尝试，失败后不补发残帧。

## 7. 操作账本与结果状态

流程：批准及能力复验 -> 全部校验 -> intent持久化成功 -> CW帧写尝试 -> 原始传输/回执证据 -> 可靠完成或unknown。记录业务operationId、完整内容/上下文摘要、地址、设备/服务实例、许可代次和证据来源。
同ID同内容返回原记录/运行状态，绝不再次触发；同ID不同内容拒绝。响应丢失后查询只作诊断，不改变核心已落盘unknown。intent/running重启恢复unknown，无自动重放。
intent前拒绝无设备副作用；现有核心错误映射仍可能保守记unknown，不能为优化显示擅改公共异常契约。

| 可观测证据 | 能说明什么 | 允许核心终态 |
|---|---|---|
| intent持久化 | 接受执行意图 | 无 |
| write/drain返回 | 传输层接受/排空字节 | 无 |
| 有效且可关联FB | 命令接受（须先证实关联） | 无 |
| 单次RX、等待时长、监听到片段 | 局部观测 | 无 |
| 操作关联完成、后续无排队发码的可靠依据 | 已完成目标操作 | completed，仅验收该证据路线后 |
| 目标操作停止且不会继续排队执行的可靠依据 | 已停止目标操作 | cancelled，仅验收该证据路线后 |
| 超时、断线、归属不明、证据不足 | 无法确定结果 | unknown并禁发 |

0x17 FF写出只记stop_requested；FB默认ack_observed，仅在已验收的关联规则成立时记command_accepted，仍不是完成/停止。操作未启动且能证明未写出时可记录未启动事实；如何映射核心终态需要专门契约设计，不能假称backend_stopped。

设备账本沿用先持久化再执行原则；真实存储schema和证据条目必须版本化。现有Fake JSONL没有防篡改/缺失检测或解除接口，不可直接宣称生产恢复已解决。
真实部署前需设计稳定设备登记、已初始化标记与账本关联、账本缺失/损坏时拒绝，以及人工设备unknown核查记录。不能靠新账本/新核心DB重建身份恢复许可；同用户恶意删除仍超出现有隔离保证。
核心解除不解除设备unknown；设备解除亦不自动批准。原unknown不可覆写成completed；解除保存操作者、证据、原因及关联操作，重新采样/新提案/新批准另行进行。解除接口和存储迁移单列设计，E前必须验收。

## 8. 停止、失联与进程生命周期

有效控制会话的stop不受旧send授权过期限制，只针对目标操作。控制失联/宿主EOF触发服务内部禁发与有界停止，不等待客户端再次连接。
业务deadline/状态变化触发一次停止流程，不重发消息。连接可用才尝试停止帧；不可用时保留unknown，界面提示人工核查，不能显示已停止。
核心/设备写入失败禁新send；即使审计写失败也应尝试可行的停止，持久化/停止失败显式报告。退出必须等待后台任务、账本刷盘及串口关闭确认；无法确认则非零退出，不报告端口已释放。
宿主不得自动重启服务/恢复发码；强杀不构成停止证明。独立硬件停机方法由D设计并现场确认，控制进程崩溃时仍可人工使用；本设计不把关闭串口当作硬件急停。
